Tu agis comme une équipe produit complète composée simultanément de :

* directeur produit ;
* architecte logiciel principal ;
* ingénieur Flutter senior ;
* ingénieur Dart senior ;
* ingénieur backend senior ;
* architecte local-first et offline-first ;
* expert SQLite, Drift et synchronisation distribuée ;

Tu dois créer une application provisoirement appelée **KUMBA Business**.

---

# 1. MISSION PRINCIPALE

Conçois et développe un **ERP mobile complet, mature, modulaire, multisectoriel, mobile-first et offline-first**, destiné aux petits commerces qui ne disposent pas nécessairement :

* d’ordinateur ;
* de serveur local ;
* de scanner professionnel ;
* de terminal d’inventaire ;
* de caisse informatisée ;
* d’imprimante ;
* de connexion Internet permanente ;
* d’un service informatique ;
* d’un budget élevé.

L’application doit transformer un téléphone Android ordinaire en :

* caisse mobile ;
* scanner de codes-barres ;
* terminal d’inventaire ;
* carnet de dettes ;
* gestionnaire de stock ;
* gestionnaire de dépenses ;
* outil de facturation ;
* terminal de livraison ;
* pointeuse simple ;
* appareil photo de preuve ;
* scanner de documents ;
* outil de suivi des employés ;
* tableau de bord de gestion ;
* assistant professionnel.

L’application doit être conçue comme un produit natif mobile à part entière.

Elle ne doit pas ressembler :

* à un site web enfermé dans une application ;
* à un tableau de bord desktop réduit ;
* à un template Flutter générique ;
* à une maquette produite automatiquement ;
* à un assemblage d’écrans sans cohérence ;
* à un prototype ou un MVP.

# 7. DIRECTION ARTISTIQUE

## 7.1 Style général

Créer un style :

> Africain contemporain + iOS 26 soft premium + interface métier épurée.

Le design doit être inspiré par :

* des surfaces lumineuses ;
* une profondeur douce ;
* des matériaux translucides contrôlés ;
* des panneaux flottants ;
* des transitions fluides ;
* une hiérarchie nette ;
* des espacements généreux ;
* des cartes propres ;
* des contrôles tactiles précis ;
* une forte lisibilité.

Il ne faut pas copier exactement l’interface Apple.

Il faut adapter ce langage visuel à :

* Android ;
* Flutter ;
* des téléphones modestes ;
* un ERP professionnel ;
* des utilisateurs non techniques ;
* une utilisation quotidienne intensive.

## 7.2 Effet verre

Utiliser l’effet verre principalement pour :

* barre de navigation flottante ;
* boutons d’action flottants ;
* menus contextuels ;
* filtres ;
* panneaux rapides ;
* sélecteurs ;
* commandes superposées ;
* assistant IA ;
* notifications importantes.

Ne pas appliquer le verre à toutes les cartes et à tous les contenus.

Les listes, formulaires, rapports et documents doivent utiliser des surfaces plus stables et lisibles.

Prévoir un mode de rendu simplifié pour les téléphones moins puissants :

* réduction du flou ;
* transparence réduite ;
* absence de shaders lourds ;
* ombres simplifiées ;
* animations réduites.

# 13. MOUVEMENT ET ANIMATIONS

Les animations doivent être discrètes, intentionnelles et rapides.

## Transitions principales

Utiliser :

* fondu léger ;
* glissement court ;
* changement d’échelle très faible ;
* morphing contrôlé ;
* déplacement partagé d’un élément ;
* feuilles modales ;
* cartes expansibles.

Durées recommandées :

* interaction rapide : environ 120 à 180 ms ;
* transition d’écran : environ 220 à 320 ms ;
* confirmation : environ 300 à 450 ms.

Ne pas ralentir l’utilisateur pour montrer une animation.

## Retours d’interaction

Prévoir :

* vibration légère ;
* changement de profondeur ;
* halo discret ;
* coche animée ;
* progression ;
* retour sonore facultatif.

## Réduction des animations

Respecter :

* préférence système de réduction des mouvements ;
* mode économie d’énergie ;
* appareils peu puissants.

# 17. IMPRESSION DE TRAVAIL HUMAIN

L’application ne doit pas donner l’impression d’avoir été automatiquement générée.

Pour cela :

* chaque écran doit répondre à un besoin précis ;
* les composants doivent être cohérents ;
* les textes doivent être contextualisés ;
* les états doivent être complets ;
* les illustrations doivent partager le même style ;
* les espacements doivent être maîtrisés ;
* les animations doivent avoir un but ;
* les formulaires doivent suivre le processus métier ;
* les erreurs doivent être spécifiques ;
* les menus doivent respecter la fréquence d’usage ;
* les données de démonstration doivent être réalistes ;
* les détails doivent être constants.

Interdictions de design :

* cartes identiques répétées sans réflexion ;
* gradients bleu-violet génériques ;
* glassmorphism partout ;
* chiffres aléatoires ;
* icônes de bibliothèques mélangées ;
* illustrations de styles différents ;
* textes génériques comme « Lorem ipsum » ;
* boutons « Submit » ;
* alignements approximatifs ;
* interfaces surchargées ;
* tableaux desktop réduits ;
* composants clonés d’un template.
